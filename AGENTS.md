# MiBatute: flujo acordado con el responsable

- Trabajar en `main`, en este checkout habitual. No crear ramas ni worktrees alternativos sin petición explícita del usuario.
- Trabajar y presentar los cambios primero en local para revisión del usuario. No hacer commit, push ni deploy hasta que el usuario lo indique explícitamente después de revisar. Cuando autorice publicar, usar main y el proyecto Vercel habitual en `https://www.mibatute.com`.
- No retirar funcionalidades o páginas a un archivo inactivo para hacer una entrega parcial sin comunicarlo y acordarlo. Mantener los pendientes legales identificados como borrador; publicarlos para revisión no equivale a aprobación jurídica.
- Conservar registro y funciones del mercado operativos durante las pruebas. Wompi y las recargas reales siguen deshabilitados en producción. El usuario autorizó integrar y probar Sandbox exclusivamente en local; nunca usar llaves de producción para esas pruebas. No marcar revisiones jurídicas como completadas ni activar borrados por publicar código.
- Correo de atención: buzón `info` del dominio `mibatute.com`. No usar Gmail. No cambiar el SMTP de autenticación de Resend por actualizar ese contacto.
- No realizar pruebas en el navegador local ni capturas. Validar por terminal cuando corresponda. Dar respuestas cortas y precisas, con el resultado y las limitaciones reales.
- El respaldo git anterior a la integración no debe aplicarse automáticamente sobre los archivos actuales. Revisar `docs/despliegue-pruebas-funcionales.md` antes de cambiar migraciones o bloqueos de registro.
